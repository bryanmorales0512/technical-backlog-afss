Project Overview
Section 1Page 3

The AFSS Backlog Tracker is an internal web dashboard that connects live to SimPRO to give management a real-time, consolidated view of the CFSP audit backlog across three companies, team availability, and scheduled technical support work.

Key Features

Backlog Table
  • Live job counts, hours & invoice amounts per company
  • Status rows: Scheduled / Tentative / Awaiting Client / Complete
  • Month filter to view jobs by scheduled date
  • Progressively loads — each company appears as data arrives
Technical Team Supply
  • Remaining billable hours per auditor for current month
  • Leave automatically deducted from SimPRO schedule data
  • Before 3 PM: today counts; after 3 PM: tomorrow starts
Technical Support Works
  • Other billable work scheduled to tech team (today → month end)
  • Invested time: pending jobs for customers being served this period
  • Quality Assurance jobs assigned to QA Officer
Performance & Automation
  • 1-hour disk cache — fast responses after warmup
  • Cloud Scheduler warms cache every 30 minutes automatically
  • Stale-while-revalidate — always serve instantly, refresh in background
  • "Refresh now" button triggers immediate background refresh

Dashboard — Tech Team Works
Section 2Page 4

The main dashboard table shows job counts, estimated hours, and invoice amounts broken down by status row and company column. All numbers update automatically from SimPRO.

Status Rows
ColourRow NameConditionNotes
Scheduled Awaiting to be Done Job has a confirmed scheduled date in SimPRO Date sourced from schedule blocks or job detail fields
Awaiting Client Info Status Name contains "client" or "awaiting" Pending jobs stuck waiting on customer action
Tentative Awaiting Scheduling Pending job with no confirmed schedule date Default bucket for unscheduled CFSP audit jobs
Attendance Complete / Results To Be Released Stage = Progress (non-AE Evac), or status name contains complete/released/attendance AE Evac Progress-stage jobs treated as Scheduled, not Complete
Month Filter

The dropdown (top-right) filters all status rows to only show jobs whose scheduled date falls in the selected month. Selecting a month also includes the previous month in results (e.g. selecting June shows May + June combined). Defaults to "All".

Total Backlog Row

The "Total Backlog as at end of period" row sums every job across all status rows and all three companies — regardless of the month filter.

AE Evac Special Rule

AE Evac (company 10) uses the Progress stage to mean "booked" rather than "attendance done." Progress jobs for AE Evac are placed in Scheduled if they have a date, or Tentative if they do not — not in the Complete row like all other companies.

Loading & Partial Data States

The dashboard uses a progressive loading strategy — each of the 6 company/stage combinations renders as soon as its data arrives, rather than waiting for all 6.

Loading Indicators
  • Loading… (blue, top bar) — fetches are still in flight
  • Refreshing schedule data… (amber) — data arrived but schedule enrichment is still running in background
  • — dashes in Scheduled & Tentative rows — enrichment not yet complete; correct split unknown until schedule data is ready
  • Updated: HH:MM:SS — timestamp of the last successful data fetch
Normal Operation

With the cache warm (Cloud Scheduler runs every 30 min), the dashboard loads with correct numbers in under 2 seconds. The dashes only appear on a cold cache (new deploy or instance restart).

Technical Team Supply

Shows the remaining billable supply hours for each of the three AFSS auditors for the current calendar month.

ColumnDescription
May (current month)Remaining working days × 8 hrs
Total Supply HoursSame — matches the SimPRO "end of period" concept
RolesEach auditor's primary function description

Working Days Calculation

Remaining Days Logic
  • Before 3:00 PM today → today counts as a remaining day
  • From 3:00 PM onwards → today is excluded (day is considered done)
  • Weekends (Sat/Sun) are never counted
  • Counts from start date through the last day of the current month

Leave Deduction

Leave is sourced from the SimPRO schedule API. Activity blocks with reference ID 1 (Annual Leave) or 2 (Sick/Personal Leave) are detected and the note at the bottom of the table lists any leave for today or upcoming in the current month.

Leave Data Source

The /api/leave endpoint scans all weekdays of the current month plus 7 days ahead (to catch pre-booked upcoming leave), fetching schedule blocks in parallel for speed.

Technical Support Works

Three columns of automated statistics, each sourced live from SimPRO with a 1-hour cache.

Other Billable Work Scheduled to Tech Teams
  • Rate: $100 per hour
  • Date range: Today → end of current month (rolling daily)
  • Scans the SimPRO schedule day-by-day for job-type blocks
  • Staff: Josh Roger, Muhammad Soban, Ryan Gordon + Tentative placeholders
  • Excludes CFSP audit jobs (tech ID 1126) and "system testing" tagged jobs
Invested Time (Training / Non-Billable)
  • Rate: $100 per hour
  • Date range: Today → end of current month
  • Finds customers with jobs scheduled to the team in this period
  • Counts all pending SimPRO jobs belonging to those customers
  • Represents pending workload of clients the team is actively serving
Quality Assurance — Overall Total in SimPRO
  • Rate: $100 per hour
  • No date filter — shows full current QA workload
  • All Pending + Progress jobs in company 1
  • Filtered to jobs assigned to "A Quality Assurance Officer" technician
SimPRO Integration & Data Logic
Section 4Page 6
CFSP Filter & Job Classification

A job qualifies as a CFSP audit job if technician ID 1126 ("A CFSP ONLY") is assigned to it. This filter applies to companies 1 and 10. Company 8 (CHUBB/AFAC) returns all jobs without filtering.

Scheduled Date Detection

A job is classified as "Scheduled" if any of these data points exist:

PrioritySourceDetails
1stSchedule blocks APIPer-job schedule blocks — most accurate, includes actual booking date
2ndJob detail fieldsChecks Scheduled, DateScheduled, ScheduledDate, DateBooked

Calculation Defaults

FieldPrimary SourceDefault if Missing
Estimated HoursTotals.ResourcesCost.LaborHours.Estimate2 hours
Invoice AmountTotal.ExTax$330
AE Evac rateHeader label only$385/hour
Rate Limiting

SimPRO enforces API rate limits (HTTP 429). All API calls use exponential backoff with up to 8 retry attempts. Initial retry delay is 1 second, doubling each attempt (1s → 2s → 4s → 8s…). Concurrent requests are capped at 10 per pool to reduce 429 frequency.

Job Enrichment Pipeline

Raw job list data from SimPRO only contains basic fields. The enrichment pipeline adds site details, confirmed schedule dates, and customer group classification per job.

1
Fetch job list (pages 1–10 in parallel)
Fetches up to 2,500 jobs per company/stage. Filters to CFSP tech ID 1126 (except company 8).
2
Parallel enrichment — 4 streams at concurrency 10
Details: /jobs/{id} — labour hours, status, all fields
Sites: /sites/{id} — site name and address
Schedules: /schedules/?JobID={id} — confirmed date + hours
Customers: /customers/{segment}/{id} — customer group
3
Merge & write cache
Enriched jobs are merged with _site, _scheduledDate, _scheduledHours, and _customerGroup fields, then written to /tmp as JSON.
Enrichment Time

Enrichment takes 30–160 seconds per company/stage depending on job count and SimPRO API speed. For 85 jobs (company 1 Pending), expect ~45 seconds. This only occurs on a cold cache — normal operation serves cached data instantly.

Caching Strategy & Performance
Section 6Page 8

All three data sources (job data, leave, tech-support) use an identical caching pattern: write enriched JSON to /tmp on first fetch, then serve from cache for 1 hour while refreshing in the background when stale.

Cache Storage & TTL
CacheFileTTL
Job data (per combo)afss-jobs-{co}-{stage}.json1 hour
Leave scheduleafss-leave-cache.json1 hour
Tech Support statsafss-tech-support-v18-cache.json1 hour
Cloud Run Ephemeral Disk

The /tmp disk is wiped when Cloud Run recycles the container (e.g. on new deployment, idle scale-down, or instance restart). After a wipe, the next user request triggers a cold cache path — the Cloud Scheduler job ensures the cache is re-warmed within 30 minutes.

Stale-While-Revalidate Flow
1
Request arrives
Check /tmp for existing cache file.
2
Cache is fresh (age < 1 hour, not partial)
Return cached data immediately. No SimPRO call needed.
3
Cache is stale or partial
Return stale/partial data immediately (fast), then trigger background re-enrichment from SimPRO. Next request gets fresh data.
4
No cache (cold start)
Fetch job list immediately (fast path), return with X-Partial: 1. Background enrichment starts. Dashboard retries every 5 s.

TimeDashboard State

5–120sDashboard retries every 5 s. Background enrichment is running.
30–160sEnrichment completes. Dashboard gets full data — correct Scheduled / Tentative split appears.

Why Sequential?

Company/stage combos are warmed one-at-a-time to avoid hammering SimPRO with 60+ concurrent API calls (which causes heavy 429 rate-limiting and slows everything down). Leave and tech-support caches are warmed in parallel alongside the sequential job warmup.

SimPRO API Connection

All data is fetched from the SimPRO REST API v1.0 using a Bearer token stored as a Cloud Run secret environment variable.

API Usage Pattern
  • Job list: GET /api/v1.0/companies/{id}/jobs/?pageSize=250&columns=…
  • Job detail: GET /api/v1.0/companies/{id}/jobs/{jobId}
  • Schedules: GET /api/v1.0/companies/{id}/schedules/?JobID={id}
  • Sites: GET /api/v1.0/companies/{id}/sites/{siteId}
  • Customers: GET /api/v1.0/companies/{id}/customers/{segment}/{id}
  • Staff: GET /api/v1.0/companies/1/staff/?pageSize=250&columns=ID,Name
  • Day schedules: GET /api/v1.0/companies/1/schedules/?Date=YYYY-MM-DD
Token Note

The SIMPRO_TOKEN env var is stripped of any leading BOM characters (﻿) and whitespace on startup to avoid authentication failures from copy-paste artifacts.

Build Time

Cloud Build typically takes 4–8 minutes to build the Docker image and deploy the new revision. The old revision stays live until the new one passes health checks.

Post-Deploy Cache Warmup

Deploying a new revision creates a fresh container — the /tmp cache is empty. Run the warmup command immediately after deploy:

# PowerShell — takes 2–5 minutes Invoke-WebRequest ` -Uri "https://bryan-technical-afss-712513641417 .australia-southeast1.run.app/api/warmup" ` -TimeoutSec 310

All 6 company/stage combos, leave, and tech-support will be cached and ready before the first user visits the dashboard.

Cloud Scheduler — Automatic Cache Warming

A Cloud Scheduler job (afss-warmup-job) automatically hits the warmup endpoint every 30 minutes, ensuring the cache is always fresh before the 1-hour TTL expires.

SettingValue
Job nameafss-warmup-job
Schedule*/30 * * * * (every 30 min, UTC)
Regionaustralia-southeast1
Target URL/api/warmup
HTTP methodGET
Attempt deadline310 seconds
StateENABLED
Why 30 Minutes?

The cache TTL is 1 hour. Warming every 30 minutes gives a comfortable buffer — even if one warmup run is slow or fails, the cache is still valid from the previous successful run. Users almost never see the slow enrichment path.
